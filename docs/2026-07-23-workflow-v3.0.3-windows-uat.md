# Workflow v3.0.3 Windows Release UAT

This runbook is for the release operator validating OTTO and LOOP24 v3.0.3 on
a real Windows host. It covers the configured Gateway contract, packaged
update path, Desktop showcase workflows, one-shot scheduling, cancellation,
approval handling, concurrency, and restart recovery.

Complete the runbook once for OTTO and once for LOOP24. Preserve the resulting
text files, screenshots, run IDs, versions, and source commits as the release
UAT evidence bundle.

## Acceptance policy

- Use published installers and a real configured Gateway. Do not substitute
  mocks for the Gateway, Electron, scheduling, approval, or restart checks.
- Start from v3.0.2 when testing the in-app update path.
- Pin Gateway v2.16.13. Earlier local release preparation accidentally exercised
  `otto-gw` v2.0.11; those results do not cover the current Gateway tool-call
  work.
- Run with the Windows account and configuration used for normal operation.
- Use fictional showcase inputs only. The bundled laptop evidence is synthetic;
  the workflow must not inspect the live Windows host.
- ACP capture contains prompt and response material. Keep it local, collect it
  only for diagnosis, and disable it after testing.
- A run passes only when the UI result and durable state agree. A toast,
  screenshot, or HTTP success alone is not proof of workflow completion.

## Evidence directory

Open PowerShell and create one directory for the complete test run:

```powershell
$uat = Join-Path $HOME 'Desktop\workflow-v3.0.3-windows-uat'
New-Item -ItemType Directory -Force $uat | Out-Null

Get-Date -Format o |
    Set-Content (Join-Path $uat 'started-at.txt')

Get-ComputerInfo |
    Select-Object WindowsProductName, WindowsVersion, OsBuildNumber,
        CsSystemType, OsArchitecture |
    Format-List |
    Out-File (Join-Path $uat 'windows-host.txt')
```

Create an OTTO and LOOP24 subdirectory for screenshots and notes:

```powershell
New-Item -ItemType Directory -Force (Join-Path $uat 'otto') | Out-Null
New-Item -ItemType Directory -Force (Join-Path $uat 'loop24') | Out-Null
```

## 1. Install and identify the current Gateway

Install the exact Gateway release that contains the current tool-call changes:

```powershell
$env:GW_VERSION = 'v2.16.13'
irm https://raw.githubusercontent.com/cmetech/otto-gateway/main/scripts/install.ps1 | iex
Remove-Item Env:GW_VERSION
```

Open a new PowerShell window. Record the binary version and Kiro location:

```powershell
$gateway = Join-Path $env:LOCALAPPDATA 'Gateway\bin\gateway.exe'
& $gateway --version |
    Tee-Object (Join-Path $uat 'gateway-version.txt')

Get-Command kiro |
    Format-List * |
    Out-File (Join-Path $uat 'kiro-command.txt')
```

The Gateway must report v2.16.13 and `kiro` must resolve to the intended
Windows installation.

## 2. Enable temporary ACP diagnostics

Use the operator-owned Gateway override file so a generated `.env` refresh
does not remove the setting:

```powershell
$gwHome = if ($env:GW_HOME) {
    $env:GW_HOME
} else {
    Join-Path $HOME '.gw'
}

$overrides = Join-Path $gwHome 'overrides.env'
New-Item -ItemType Directory -Force $gwHome | Out-Null

$overrideLines = if (Test-Path $overrides) {
    @(Get-Content $overrides)
} else {
    @()
}

$overrideLines = @(
    $overrideLines |
        Where-Object { $_ -notmatch '^\s*ACP_CAPTURE\s*=' }
)
$overrideLines += 'ACP_CAPTURE=true'
$overrideLines |
    Set-Content -Path $overrides -Encoding ascii

& "$env:LOCALAPPDATA\Gateway\scripts\gw.bat" restart
```

Verify serving health and capture:

```powershell
$health = Invoke-RestMethod http://127.0.0.1:18080/health
$health |
    ConvertTo-Json -Depth 10 |
    Tee-Object (Join-Path $uat 'gateway-health.json')

$capture = Invoke-RestMethod `
    http://127.0.0.1:18080/admin/api/acp-capture
$capture |
    Select-Object enabled, size, allowRuntimeToggle |
    Format-List |
    Tee-Object (Join-Path $uat 'gateway-capture-status.txt')
```

Required result:

- `health.status` is `ok`;
- `health.pool.alive` is greater than zero;
- capture `enabled` is `True`.

2. **Update now** downloads the correct brand's installer;
3. the installer identifies as OTTO or LOOP24, never the other brand;
4. after relaunch, the shell reports v3.0.3;
5. the first post-update bootstrap converges the backend clone to the release's

$ottoRoot = Join-Path $env:LOCALAPPDATA 'otto\hermes-agent'

## 4. Run the configured-Gateway parity gate

The harness calls the Gateway directly over each supported API surface. It
does not execute arbitrary output as a tool.

For OTTO:

```powershell
$env:GW_URL = 'http://127.0.0.1:18080'
$python = Join-Path $ottoRoot 'venv\Scripts\python.exe'
$parity = Join-Path $ottoRoot `
    'skills\gateway-toolcall-parity\run_parity.py'

& $python $parity --suite conformance 2>&1 |
    Tee-Object (Join-Path $uat 'otto\gateway-conformance.txt')
$ottoConformanceExit = $LASTEXITCODE

& $python $parity --suite toolcall --retries 3 2>&1 |
    Tee-Object (Join-Path $uat 'otto\gateway-toolcalls.txt')
$ottoToolcallExit = $LASTEXITCODE
```

For LOOP24:

```powershell
$python = Join-Path $loop24Root 'venv\Scripts\python.exe'
$parity = Join-Path $loop24Root `
    'skills\gateway-toolcall-parity\run_parity.py'

& $python $parity --suite conformance 2>&1 |
    Tee-Object (Join-Path $uat 'loop24\gateway-conformance.txt')
$loop24ConformanceExit = $LASTEXITCODE

& $python $parity --suite toolcall --retries 3 2>&1 |
    Tee-Object (Join-Path $uat 'loop24\gateway-toolcalls.txt')
$loop24ToolcallExit = $LASTEXITCODE

[pscustomobject]@{
    OttoConformance = $ottoConformanceExit
    OttoToolcalls = $ottoToolcallExit
    Loop24Conformance = $loop24ConformanceExit
    Loop24Toolcalls = $loop24ToolcallExit
} |
    Format-List |
    Tee-Object (Join-Path $uat 'gateway-exit-codes.txt')
```

Required result:

- all non-SKIP conformance checks pass;
- all eight tool-call checks pass for each brand;
- weather calls surface as structured `get_weather(city="Paris")`;
- the nested-fence case surfaces `write_file` and preserves its fenced content;
- execute cases surface structured `run_shell`, not textual `[tool: ...]`;
- an invented name is remapped to the sole tool offered by the client;
- every captured exit code is zero.

If a tool-call check fails, preserve the harness output and the capture response:

```powershell
Invoke-RestMethod `
    http://127.0.0.1:18080/admin/api/acp-capture |
    ConvertTo-Json -Depth 30 |
    Set-Content (Join-Path $uat 'acp-capture-on-failure.json')
```

Do not upload that capture to a public issue.

## 5. Desktop preflight for each brand

Perform the remaining sections once in OTTO and once in LOOP24.

Before starting:

1. Confirm Settings → About shows v3.0.3.
2. Confirm the active provider is the current brand's Gateway profile using
   `auto` at `http://127.0.0.1:18080/v1`.
3. Confirm Gateway health remains green.
4. Open Workflows and confirm the showcase catalog loads without an error.
5. Confirm the English trust label reads exactly **verified bundle**.
6. Confirm any incompatible row has Run disabled in the catalog, View dialog,
   and Review & Run dialog.
7. Confirm unsupported-input guidance comes from the server-provided reason
   and directs the operator to the CLI where appropriate.

For every run below, record:

- brand;
- showcase name;
- run ID;
- start or scheduled instant;
- approval/rejection/cancellation action;
- terminal state;
- artifact names;
- screenshot filename;
- any unexpected toast or log message.

## 6. Laptop Diagnostic Tour — approval path

1. Select **Laptop Diagnostic Tour**.
2. Enter:

   `A fictional Windows laptop starts slowly after an update.`

3. Start the workflow.
4. Confirm it uses only the bundled fictional evidence. It must not enumerate
   the Windows host, installed applications, network, or hardware.
5. Wait for `review-plan` to pause in Attention.
6. Approve with the comment:

   `Approve the fictional diagnostic plan.`

7. Wait for `Succeeded`.

Required result:

- the five analysis nodes complete and fan in to report rendering;
- exactly one approval is pending before the decision;
- `finalize-plan` runs only after approval;
- the run produces:
  - `diagnostic-report.json`;
  - `diagnostic-report.md`;
  - `remediation-plan.md`;
- no remediation command executes against Windows.

## 7. Laptop Diagnostic Tour — bounded rejection path

Start a new Laptop Diagnostic run with the same fictional symptom.

1. At the first approval, reject with:

   `Keep every fictional action manual.`

2. Confirm the run performs exactly one deterministic rework and pauses again.
3. Confirm a `rework-output.txt` artifact exists.
4. Reject the second approval with:

   `End the bounded rejection test.`

5. Wait for `Cancelled`.

Required result:

- the first rejection does not execute a real AI runner or live remediation;
- exactly one rework attempt is recorded;
- the second rejection exhausts the bounded rework path;
- the durable run remains cancelled after leaving and reopening Workflows.

## 8. Optional AI and Extensions Tour

Keep the configured Gateway running.

1. Select **Optional AI and Extensions Tour**.
2. Confirm the row is runnable. If it is unavailable, capture its complete
   server-derived reason rather than forcing admission.
3. Start the workflow.
4. Wait for both `inspect` and `continue` to finish.
5. Wait for `Succeeded`.

Required result:

- inference travels through the configured brand Gateway;
- the hook, bundled skill, inline reviewer agent, persistent session, and local
  echo MCP are available to the intended nodes;
- the output satisfies the declared `summary` and `simulated` object shape;
- the second node reuses only its intended persistent session;
- the local MCP process is cleaned up after the run;
- no provider/model traffic occurs before a required MCP startup failure.

## 9. Run later → Scheduled → due success

Use **Optional Scheduling Tour** for the deterministic scheduling check.

1. Select **Run later**.
2. Choose an instant three to five minutes in the future.
3. Submit the run.
4. Record the local display time and canonical UTC instant from the inspector.
5. Confirm the run displays `Scheduled`, not an immediate queue position.
6. Keep the Desktop backend running through the due instant.
7. Wait for `Succeeded`.

Required result:

- the server accepts one canonical future instant;
- the run remains `scheduled_wait` before that instant;
- it does not occupy an immediate worker or concurrency lane while waiting;
- it promotes no earlier than the due instant;
- it executes exactly one `checkpoint` node;
- `scheduled-checkpoint.json` exists once;
- repeated refreshes do not duplicate execution or notifications.

## 10. Cancel before fire

1. Schedule another Optional Scheduling Tour at least five minutes ahead.
2. Confirm it displays `Scheduled`.
3. Cancel it from the run inspector.
4. Record the cancellation state and run ID.
5. Leave the Desktop backend running until at least one minute after the
   original due instant.
6. Refresh the run and restart Desktop.

Required result:

- the run remains `Cancelled`;
- no node is claimed or executed;
- no scheduled checkpoint artifact appears;
- its durable run history remains inspectable;
- restarting after the due instant does not resurrect it.

## 11. Scheduled AI fire-time revalidation

1. Schedule **Optional AI and Extensions Tour** five minutes ahead.
2. Confirm it displays `Scheduled`.
3. Restart Gateway before the due instant and re-check Gateway health.
4. Restart Desktop before the due instant.
5. Confirm the same run ID and scheduled instant survive both restarts.
6. Keep Gateway healthy through the due instant.
7. Wait for `Succeeded`.

Required result:

- fire-time eligibility is derived from the current configured Gateway and
  runtime, not stale process-start state;
- the run does not claim a node before revalidation;
- the local MCP and AI nodes run once;
- restart recovery does not duplicate the run.

## 12. Approval Gate regression

1. Run **Approval Gate Tour**.
2. Confirm it pauses with exactly one approval in Attention.
3. Approve it.
4. Wait for `Succeeded`.
5. Reopen the run after restarting Desktop.

Required result:

- approval is consumed once;
- double-clicking Approve cannot submit two decisions;
- the succeeded state survives restart;
- no stale approval returns to Attention.

## 13. Multi-workflow concurrency and restart recovery

This test exercises the coordinator under the load pattern most likely to
expose scheduling starvation or duplicate recovery.

1. Schedule three Optional Scheduling Tour runs for the same future minute.
2. Schedule one Optional AI and Extensions Tour for that minute.
3. Immediately start one Laptop Diagnostic Tour.
4. Record all five run IDs and states.
5. While the Laptop Diagnostic is active and the scheduled runs are waiting,
   quit Desktop completely.
6. Reopen Desktop before the due instant.
7. Confirm every run reappears with its original run ID and scheduled instant.
8. Cancel one of the three deterministic scheduled runs.
9. Approve the Laptop Diagnostic if it is paused.
10. Let the due instant pass with Gateway healthy.
11. Wait for all non-cancelled runs to reach terminal states.
12. Restart Desktop again and inspect every run.

Required result:

- the immediate Laptop Diagnostic is not starved by the scheduled backlog;
- waiting runs do not consume immediate queue positions or workers;
- the cancelled run never executes;
- the remaining deterministic runs each execute exactly once;
- the scheduled AI run revalidates and executes exactly once;
- no duplicate artifacts, approvals, terminal notifications, or run IDs appear;
- coordinator restart preserves admission order and makes forward progress;
- one damaged or failed run does not prevent healthy peer runs from advancing.

An ordinary Remote Desktop disconnect is acceptable while the app continues
running. Signing out terminates user processes and should be treated as a
deliberate restart case, not as passive waiting.

## 14. Negative scheduling and compatibility checks

Exercise these without attempting to bypass the UI:

1. Enter a past Run later time. Submission must be blocked with localized,
   accessible feedback.
2. Enter an invalid or incomplete local time. Submission must be blocked.
3. Open an incompatible catalog row. Run must remain disabled everywhere.
4. Temporarily stop Gateway and refresh the AI Extensions row. Its availability
   must fail closed with an actionable reason; it must not silently run using a
   different provider.
5. Restart Gateway and refresh. Availability must recover without reinstalling
   the product.

Do not mutate the packaged showcases, trust store, or authenticated sidecars to
force a negative result on the release machine.

## 16. Disable ACP capture

After collecting any necessary failure evidence:

```powershell
$overrideLines = @(
    Get-Content $overrides |
        Where-Object { $_ -notmatch '^\s*ACP_CAPTURE\s*=' }
)
$overrideLines += 'ACP_CAPTURE=false'
$overrideLines |
    Set-Content -Path $overrides -Encoding ascii

& "$env:LOCALAPPDATA\Gateway\scripts\gw.bat" restart
```

Confirm capture is no longer enabled. If the endpoint is absent after restart,
that is also an acceptable disabled state.

## Release UAT exit criteria

Release UAT is complete only when:

- the exact Gateway and product versions are recorded;
- every non-SKIP Gateway conformance check passes;
- structured tool-call parity is 8/8 for both installed brand copies;
- all required showcase, approval, scheduling, cancellation, and recovery rows
  pass for both brands;
- any failure includes its run ID, screenshot, relevant Desktop/Gateway logs,
  and ACP capture when needed;
- ACP capture is disabled at the end;
- the completed evidence directory is retained with the release record.
