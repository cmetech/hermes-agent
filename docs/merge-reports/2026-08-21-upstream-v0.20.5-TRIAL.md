## Fix acceptance and decline analysis

No fix was declined because its conflict was difficult. Decisions were based on
runtime need, intent, fork policy, and whether upstream supplied an equivalent:

- Accepted and adapted upstream lifecycle, lease, profile, cache, accessibility,
  workflow, and plugin changes where they fix active behavior.
- Removed the redundant `hermes version` command path because upstream
  `--version`/`-V` is equivalent. This is cataloged as
  `remove-downstream-as-equivalent`, not a lost feature.
- Retained `User-Agent: HermesAgent/<version>` for Kimi requests but did not
  take upstream `HTTP-Referer` and `X-Title` attribution headers. They are not
  required for the transport fix and violate the fork's no-attribution-without-
  opt-in policy. Revisit only after a generic user-facing telemetry opt-in
  exists.
- No upstream bug fix was cataloged as permanently unnecessary solely to avoid
  resolution work.

This is the intended future rule: a hard conflict triggers an importance and
intent review, never an automatic waiver. A declined change must record the
upstream behavior, reachability, user impact, policy reason, replacement (if
any), and the condition that would cause reconsideration.
