**Candidate defects I developed and deliberately did not promote to findings.** Each is disclosed with the specific proof element it failed, so my judgment can be checked:

1. **`known_no_effect=True` for a definitively *failed* handoff** (`scheduler.py:6304-6327`). `definitive_handoff` forces `outward_action=False` and `known_no_effect=True` whenever the handoff reached `succeeded`/`failed`/`cancelled`. Assignments are *required* to be declared outward (`schema.py:2607`), so this removes outward-action protection from every assigned node. Traced concretely: with `retry.on_error: "all"` (non-default; default is `"transient"`, `max_attempts=5`), `classify_failure("handoff_remote_failed", known_no_effect=True, outward_action=False)` → `UNKNOWN_ERROR` → converted to `TRANSIENT` → `schedule_retry`, creating a new handoff generation and re-executing the destination prompt. Pre-change, `outward_action=True` short-circuited to `UNKNOWN_OUTCOME` → `paused` awaiting operator reconciliation. Asserting "no effect" for a destination agent that demonstrably ran is factually wrong. **Not promoted** because the authoritative plan explicitly sanctions this ("increment the generation only after a definitive, policy-authorized retry"; "Validation failure follows existing Workflow retry authority"), so I cannot prove a violated invariant rather than a contested design choice. Worth a maintainer decision.

2. **Foreground execution mode never advances handoffs.** `advance_due_handoffs` is called only for `execution_mode == "background"` (`coordinator.py:436`). `RunScheduler.advance()` — the foreground driver at `cli.py:2414` — does not call it. So `hermes workflow run <assigned-wf> --foreground` binds the handoff, parks the node in `waiting_handoff`, releases the foreground lease, and **returns exit 0 printing status `running`**. Note the mode is documented for exactly the case where the coordinator is unhealthy (`cli.py:2350`). **Not promoted** because the run self-heals: `release_foreground_execution` writes an already-expired lease, so any coordinator that later starts adopts the run via `adopt_expired_foreground`, flips `execution_mode` to `background`, and converges. The permanently-stuck case requires no coordinator to ever run again — and foreground runs already park identically on `waiting_retry`, so this is the codebase's established foreground→coordinator handover, not a new hazard. It fails the "concrete wrong result" element. Still, a warning line when a foreground run parks on `waiting_handoff` would be cheap and would remove the misleading exit-0/`running` signal.

3. **Reconcile re-POSTs `/v1/runs` after a durable cancel.** `journal_attempt` explicitly refuses `operation == "submit"` on a cancelled handoff (`store.py:767-770`), but `_select_operation` routes a cancelled, submit-attempted, `run_id`-less handoff to `reconcile`, and `LocalHermesChannel.reconcile` falls through to `self._submit(...)` (`local.py:1156`). If the original POST never reached the server, this **creates** the destination Run for an already-cancelled handoff. **Not promoted:** replaying the exact body and idempotency key is the only way to learn the `run_id` needed to stop it, the very next advance issues the stop, and the plan prescribes this reconciliation. Converges correctly; no durable wrong state.

4. **Destination reports `stopping` with no local cancel command.** `_observe` returns `phase="cancelling"`, which `commit_observation` rejects (no durable cancel fact); `_fold`'s `except HandoffStateConflict` branch re-raises the identical conflict, so the observation is silently dropped with `next_advance_at=None`. **Not promoted:** the scheduler's `next_advance_at or observed + timedelta(seconds=5)` floor caps re-polling at 5 s (no hot loop, no starvation), `state_version` still advances via `release_advance`, and the handoff converges as soon as the destination reaches a real terminal status. No data loss, no wrong terminal state. Cosmetically, the ledger does not record that the destination is stopping during that window.

5. **Notification dedup ignores `dismissed`/`delivered` state.** A new actionable event for an already-acknowledged `(node, handoff_id, generation)` updates the existing row's payload without re-surfacing it. **Not promoted:** per-generation identity is the stated, ledger-owned design ("each handoff failure notification has an exact durable identity"), and dismissal reasonably means "this generation is handled."

6. **`_migrate_notification_handoff_identity` re-scans every NULL-handoff outbox row on each `install_notification_schema`.** All non-handoff notifications have NULL handoff columns, so the "incremental" path is O(all non-handoff rows) per outbox construction. **Not promoted:** `NotificationOutbox._from_initialized_store` keeps this off the hot path, `test_performance_bounds.py` passes, and I could not demonstrate a production wrong result.

This is **stricter** than specified and better serves invariant 17, at the cost of losing stderr for diagnostics. The plan text and the code should be reconciled in one direction.
