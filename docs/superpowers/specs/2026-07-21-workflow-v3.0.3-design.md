**Date:** 2026-07-21 (Revision 7 — final pre-implementation contract)

**Release:** v3.0.3, paired OTTO and LOOP24 release

## Revision 7 note

Revision 7 closes the final real-worker MCP review and rebuttal without
reintroducing consent or adding a test-only production switch. It retains the
Revision 6 decisions and adds these load-bearing corrections:

- **Legacy entitlement is fail-closed.** Existing REST showcase runs carry
  `showcase_provenance=verified_bundled`, but v3.0.2 CLI showcase runs do
  not. Missing entitlement now derives `deterministic` for either the marker
  or the legacy immutable showcase metadata tuple. Explicit `real` is valid
  only when it is corroborated against the exact verified `requires_ai`
  scenario.
- **Authenticated cache contents are truly context-free.** The verified
  cache stores the parsed scenario/package snapshot and authenticated
  package/bundle digests only. Compatibility and `WorkflowRiskSummary` are
  both recomputed per execution context because the current risk digest
  includes compatibility.
- **CLI behavior is honest.** The AI confirmation token is removed, but the
  deterministic CLI tour remains MCP-incapable and therefore continues to
  report `ai-extensions` as incompatible. v3.0.3 unlocks the scenario on
  Desktop/background only; a future MCP-capable CLI tour is separate scope.
- **Existing REST values remain compatible.** Declared text inputs receive
  strict declaration/binding validation, while legacy flat workflows with
  no input declaration retain their existing bounded portable `values`
  contract. Showcase-reserved keys are scoped to verified-showcase
  admission.
- **Capability is runner- and runtime-sensitive.** Entitlement authorizes
  agent-backed execution but cannot manufacture MCP support. The runner must
  start request-carried MCP and the resolved runtime must return tool calls to
  Hermes' tool loop; unknown or externally owned tool-loop modes fail closed.
  The OTTO/LOOP24 HTTP gateway and `copilot-acp` contracts use the Hermes loop;
  `codex_app_server` does not and remains incompatible with package MCP.
- **The isolated worker owns the complete MCP lifecycle.** It explicitly
  discovers request-carried servers before tool-policy validation, refuses a
  failed required server before model traffic, and shuts every server down
  from an outer cleanup boundary covering all early exits. A localhost mock
  provider proves tool-schema delivery and process reaping without external
  network or billable inference.
- **Immediate binding identity is pinned, not revalidated through a new run
  state.** Admission and coordinator construction use the same immutable
  production binding factory. The worker independently rejects a changed or
  unsupported actual runtime. Scheduled runs retain full fire-time
  revalidation because time, restart, and configuration changes are inherent
  to that feature.
- **Input translation and schedule reconstruction are explicit.** Public
  showcase values are translated only after authenticated metadata resolves
  and before snapshot preparation; raw bytes never project, while their
  manifest digest intentionally participates in idempotency. Namespace/table
  rebuilds insert `scheduled_at` only from corroborated projection metadata,
  never from an old SQL column.
- **Execution limits are exact.** `RunExecutionLimits` now enumerates only
  existing sidecar-schema fields and maps every field to its enforcement
  point. The nonexistent run-level `max_iterations` field is withdrawn.
- **Scheduling is self-contained.** The complete schema, recovery, wake,
  fairness, clock, revalidation, cancellation, UI, failure, and test
  contracts are restored below and in the plan. No overwritten revision is
  normative.

Consent tokens, consent dialogs, HMAC key scope, and consent×schedule
composition remain intentionally absent. If the deployment becomes
multi-tenant or permits remote operators, AI admission requires a new threat
model before being exposed there. Revision 7 is the implementation baseline;
no further pre-implementation adversarial-review gate is required.

## Workstream 2 — rich inputs and execution honesty

### W2-0: exact `RunExecutionLimits`

`RunExecutionLimits` is a frozen record resolved from the profile defaults
and the immutable sidecar sealed into the run snapshot. It contains only
fields that are legal in the existing `WorkflowRuntimeConfig` sidecar schema.
Every numeric field is the element-wise minimum of profile and sidecar; no
field can loosen the profile.

| Fields | Scope | Enforcement point |
|---|---|---|
| `max_parallel_nodes` | per run | ready/claim selection for that run; shared scheduler pools remain profile-sized |
| `max_total_workers` | per run and global | per-run claimed-worker count composed with the existing store-global ceiling |
| `ai_idle_timeout_seconds`, `ai_wall_timeout_seconds`, `provider_request_timeout_seconds` | per agent-backed node | `NodeExecutionContext` deadline budget → corresponding `PluginAgentRunRequest` fields |
| `combined_retries` | per agent-backed node | `NodeExecutionContext.max_provider_attempts` → `PluginAgentRunRequest.max_api_attempts` |
| `subprocess_timeout_seconds` | per subprocess node | executor deadline/managed-process timeout |
| `process_tree_rss_bytes`, `process_tree_cpu_seconds`, `max_descendants` | per worker/process tree | `ResourceLimits` → worker request/managed process tree |
| `cooperative_shutdown_seconds`, `term_grace_seconds`, `kill_reap_grace_seconds` | per spawned process/agent worker | `TerminationPolicy` → process/worker request |

The following stay profile-global and are intentionally absent from the
record: `max_executing_runs`, `max_queued_runs`, `max_paused_runs`,
`max_nonterminal_runs`, `max_start_requests_per_minute`, heartbeat/lease,
coordinator election and stall thresholds. Their accepted sidecar syntax and
existing CLI/foreground semantics are unchanged; they do not resize or retime
the shared background coordinator.

There is **no** run-level sidecar `max_iterations` field. Agent-node requests
retain the existing hard cap of 90; inline-agent `maxTurns` and loop
`max_iterations` retain their existing node-schema caps. Adding a general
run-level iteration budget would require a separately designed schema and is
out of scope.

The coordinator threads `RunExecutionLimits` into per-run claim selection
and node execution without mutating the shared scheduler. Tests must cover
every row above plus a mixed-run concurrency case: run A (parallel 1, workers
2) and run B (parallel 4) execute simultaneously; A never exceeds its limits,
B reaches its own allowance, the global ceiling holds, and neither record
leaks into the other run.

### W2-1: per-run AI entitlement (H3 + M2 amendments)

**Classification.** One central, positively-defined function,
`agent_backed_features(definition)`, enumerates every agent-runner
consumer: `command` nodes, `prompt` nodes, **`loop` nodes**, inline
agents, and approval `on_reject` rework. It is the single source for
(a) the bundle-verification validator — a `requires_ai: false` scenario
may contain **no** agent-backed feature except approval rework (which
the entitlement below renders deterministic) — and (b) execution
enforcement, which is applied at **every** consumer (`AgentNodeExecutor`,
`LoopExecutor`, `ApprovalExecutor` rework), each with its own execution
test under deterministic entitlement.

**Entitlement semantics — absence is the defined value.** No entitlement key
is written for an existing run class. `derive_ai_entitlement` applies this
ordered policy:

1. An absent key is `deterministic` when metadata contains either the current
   authenticated marker (`showcase_provenance=verified_bundled`) **or** the
   complete legacy showcase identity tuple (`showcase_id`,
   `showcase_version`, `bundle_digest`, `risk_digest`). The legacy tuple is a
   fail-closed classification signal, not a grant of authority; spoofing it
   can only remove model access.
2. An absent key on an ordinary trusted user workflow without either
   showcase shape is `real`, preserving the v3.0.2 contract.
3. Explicit `ai_entitlement=real` is accepted only when the run also carries
   the current verified marker and immutable scenario identity that resolves
   to the exact digest-verified `requires_ai: true` scenario. A missing,
   non-AI, changed, or uncorroborated scenario makes the entitlement
   `deterministic` and records a typed execution-integrity failure; it never
   silently falls back to a real runner.
4. Unknown or malformed values are `deterministic`.

The rule covers current REST showcase runs, legacy CLI showcase runs, journal
recovery, and queued/running foreground runs adopted after their owner lease
expires. It does not claim paused runs are coordinator-adoptable; paused runs
remain outside the sweep until an authorized transition makes them runnable.

Existing golden and v3.0.2 start digests remain byte-identical. Required
fixtures include both a v3.0.2 REST showcase row with the marker and a
v3.0.2 CLI laptop-diagnostic row without it. Same-key resubmission joins
`existing`; foreground adoption plus rejection of the CLI fixture stays
deterministic under `HERMES_OFFLINE=1`; explicit real on a non-AI or
uncorroborated scenario fails closed; every agent-backed executor has a
zero-real-runner test.

### W2-2: input contract

The authenticated showcase catalog gains two optional mappings:

```yaml
input_fixtures:
  evidence: fixtures/laptop-evidence.json
input_value_bindings:
  symptom: arguments
```

`input_fixtures` maps a declared file-input name to a digest-covered,
package-relative POSIX path. `input_value_bindings` maps a public Desktop
field name to a declared internal text-input name. Source and target names
must be portable and one-to-one; targets must be declared with the matching
kind; duplicate targets and binding/fixture overlap are invalid. Fixture
paths reject absolute paths, `..`, empty components, lexical escape,
symlinks, non-regular files, and resolved escape from the package tree.
Because this metadata and every fixture are covered by `digests.json`, a
mapping or byte change requires a full authenticated restamp.

Verified fixture bytes are read once through the forced-verification resource
budget and passed to a new internal `verified_inputs` snapshot channel as
bytes plus expected digest. Snapshot preparation never reopens a fixture
path. The existing `inputs=` path remains for local callers and user upload
remains out of scope.

The authenticated admission boundary owns translation. After the selected
showcase and its catalog metadata have been force-verified, but before
`prepare_run_snapshot`, `api_admission` validates the public names, removes
them from the caller-value map, maps `symptom` to the declared internal
`arguments` text input, and supplies `evidence` only through
`verified_inputs`. Neither the Desktop request nor any caller-controlled
metadata can submit an internal target or fixture-owned name. No other layer
may reopen the fixture or repeat the public-to-internal translation.

**REST compatibility has two modes:**

- When a package declares inputs, client values must match the declared
  public text fields (or the verified showcase's public binding names), all
  required inputs must be present, and undeclared names are rejected typed.
  Internal binding targets and fixture-owned names are reserved only for
  `catalog_source=showcase` and cannot be submitted directly there.
- When a legacy flat workflow declares no inputs, the existing public
  bounded-portable `values` contract is unchanged, including conventional
  keys such as `arguments` and arbitrary portable keys such as `subject`.
  This compatibility mode does not apply to verified showcase bindings.

The REST distinction is a server-derived property of the selected package;
the caller cannot opt into legacy mode for a declared-input package.

**Typed REST bounds, relocated.** The per-value (64 KiB) and aggregate
(256 KiB) byte-cap checks move **out of the Pydantic model validator
into typed validation inside the endpoint path** (identical limits,
evaluated before any package work), returning the documented
`workflow_input_too_large` envelope. Structural request-shape validation
(field types, entry-count cap, name shape) remains Pydantic. Required
tests through real middleware: a 70 KiB value and a >256 KiB aggregate
each yield the typed envelope; an unrelated schema error (e.g. wrong
type for `workflow`) still yields an ordinary FastAPI validation
response — nothing unrelated is mislabeled.

For declared inputs, the effective byte bound is
`min(64 KiB REST value cap, declared sidecar max_bytes)`; the 256 KiB REST
aggregate remains an independent request cap. Store enforcement applies the
declared `max_bytes` to text, local file, and verified-fixture channels and
returns the same typed input vocabulary at the API boundary. Input values and
fixture bytes remain absent from `run_metadata`, list/detail/run projections,
evidence, audit, errors, and logs; only names, kinds, bounds, sizes, and
digests may project. The sealed input-manifest digest intentionally remains
part of the start/idempotency digest, so a changed symptom or fixture identity
conflicts rather than joining; raw bytes and raw text never enter that digest
material directly.

### W2-3: laptop-diagnostic E2E

The real-middleware E2E covers both branches: approve → succeeded, and reject
→ deterministic rework under `HERMES_OFFLINE=1` with zero real-runner
invocations → bounded outcome. It asserts store/trust/run-directory byte
snapshots, fixture manifest SHA equality, no source-path reopen, exact
provenance, merge-gate/CI membership, and installed-distribution fixture
availability.

## Workstream 3 — AI showcase enablement

### W3-0: runner- and runtime-sensitive execution capability

Entitlement and capability are separate inputs. Entitlement answers whether a
run may use an agent-backed executor. Package MCP additionally requires both a
runner that owns the request-carried MCP lifecycle and a runtime whose model
responses return tool calls to Hermes' normal tool loop:

```python
@dataclass(frozen=True, slots=True)
class RunnerCapabilities:
    starts_request_mcp: bool

@dataclass(frozen=True, slots=True)
class ExecutionRuntimeCapabilities:
    api_mode: str
    hermes_managed_tool_loop: bool
```

The workflow plugin owns a `WorkflowRunnerBinding` that pairs the selected
runner with `RunnerCapabilities`. A pure, server-owned runtime classifier
derives `ExecutionRuntimeCapabilities` from configured provider/model/runtime
metadata without resolving credentials, spawning a provider, or making a
network request. It must stay in parity with the actual runtime resolver.
Unknown future modes fail closed. OTTO/LOOP24's OpenAI-compatible HTTP gateway
profiles, ordinary OpenAI/Anthropic-compatible modes, and `copilot-acp` return
tool calls to Hermes and classify `hermes_managed_tool_loop=True`.
`codex_app_server` owns its loop and tool surface, classifies `False`, and is
not package-MCP-capable in v3.0.3.

`execution_capability_context(surface, entitlement, runner_capabilities,
runtime_capabilities)` returns `mcp_available=True` only when entitlement is
real, the selected surface is allowed to use the runner, the runner starts
request MCP, and the runtime uses Hermes' tool loop. The shared deterministic
showcase binding declares `starts_request_mcp=False`. A test binding must
declare its runner and runtime capabilities explicitly; neither entitlement
nor an arbitrary caller-supplied object may manufacture them.

Catalog/detail/admission use the immutable production binding factory plus the
pure prospective runtime classification. Coordinator construction uses that
same binding factory; an invariant test pins those two production declarations
instead of adding an unreachable immediate-run revalidation state. The actual
worker independently classifies its resolved runtime and fails
`package_mcp_unavailable` before an agent/model request if the runtime changed
or is unsupported. W4 scheduled revalidation recomputes both runner and
runtime capabilities at fire time because configuration, process, and time
boundaries are intrinsic there.

One context object threads through user and verified-showcase catalog
projection, detail, admission, and W4 fire-time revalidation; there is no
showcase-ID special case. Callers cannot submit or override it. Internal CLI
projection helpers retain their existing explicit argument semantics, but
`workflow showcase run` has no hidden capability flag and its deterministic
runner remains incapable.

**Isolated-worker lifecycle.** `PluginAgentRunner` may declare
`starts_request_mcp=True` only after its worker implements this sequence:

1. deserialize and interpolate only request-carried MCP definitions;
2. resolve and classify the actual runtime before model execution;
3. reject a non-Hermes-managed runtime before starting an agent;
4. explicitly discover/start every enabled request MCP server before
   tool-policy validation, and require each server to connect;
5. build the agent/tool snapshot only after registration; and
6. from one outer `finally`, shut down MCP and restore loader/timeout/callback/
   inline-tool/session state for discovery, validation, runtime, session,
   skill, agent, cancellation, and success exits.

A required node MCP is fail-closed: startup failure produces typed node error
`package_mcp_unavailable` with zero provider requests. This is deliberately
different from cron's optional profile-global MCP discovery, which remains
non-fatal and unchanged. `ai-extensions` is the only bundled workflow with
node-level MCP; user-authored node MCP was already blocking or nonfunctional,
so this activates the declared required-resource contract rather than
regressing a working optional-MCP path.

**Cache separation.** The cache key remains bundle digest plus tree signature,
but a cache entry contains only the authenticated scenario, immutable parsed
package snapshot, package digest, bundle digest, and the resource/tree data
needed to prove that snapshot. It contains neither `CompatibilityReport` nor
`WorkflowRiskSummary`: the current risk digest includes compatibility and is
therefore context-dependent. Projection, admission, and fire-time
revalidation recompute compatibility and then risk from the cached package
under the same execution context.

Required coverage has three layers:

1. capable and incapable catalog/detail/admission requests served from the
   same cache entry produce their own compatibility and risk digests without
   stale-state rejection; and
2. a real `PluginAgentRunner` subprocess carries the package-local echo MCP
   definition into the isolated worker, sends its registered tool schema to a
   localhost mock provider, and proves PID startup and reaping, parent-registry
   isolation, and cleanup on success and every early failure. Separate tests
   prove a failed server and `codex_app_server` both make zero provider
   requests. No test-only production flag or external/billable provider is
   introduced. The coordinator E2E may use a declared-capable test binding,
   but it must not be cited as proof of the real worker lifecycle; and
3. generated OTTO and LOOP24 provider profiles classify as the
   Hermes-managed HTTP loop, while the existing gateway tool-call parity
   contract remains the evidence that their ACP-backed gateway returns
   structured OpenAI `tool_calls` rather than prose.

### W3-2: execution and tests

Admission records `ai_entitlement=real` for the exact verified AI showcase;
the entitlement is corroborated again before runner selection. The
coordinator's normal `PluginAgentRunner` executes the command nodes

## Workstream 4 — background scheduling

### W4-0: admission identity and schema 14

`StartRunRequest` gains optional `schedule_at`. When present, it accepts a
timezone-aware RFC 3339 instant, normalizes it to UTC with a `Z` suffix, and
rejects a naive, malformed, or non-future value with typed 422
`workflow_schedule_invalid` before snapshot creation. Absence means immediate
admission for ordinary workflows; the scheduling showcase alone returns typed
409 `workflow_schedule_required` because its advertised outcome requires a
deferred start.

The API writes the canonical value to `run_metadata.schedule_at` before both
start-digest implementations run. That metadata value is the durable source
of truth. Requests without `schedule_at` retain byte-identical v3.0.2 start
digests; schedule-bearing requests intentionally have a distinct identity.
The public request never accepts arbitrary run metadata.

Store schema 13→14 adds nullable `runs.scheduled_at` and a partial index for
published queued scheduled rows. The column is a derived search/index field,
never an authority. Fresh insert, reservation publication,
`_rebuild_admission_row`, every integrity-index sync, namespace/table rebuild,
and journal recovery derive it from the projection's canonical
`run_metadata.schedule_at`; a parity assertion refuses a row whose column and
projection disagree. A namespace/table rebuild adds `scheduled_at` to the new
table schema and INSERT target list, but computes every inserted value from
corroborated projection metadata regardless of whether the source SQL table
has a column; it never reads or copies `row["scheduled_at"]`. Migration
backfills from corroborated projections and fails closed into repair for
malformed evidence. A v14 database is refused by v13 code through the existing
newer-schema guard.

Every scheduled run is admitted with `execution_mode=background` and
projection status `queued`. No new status is stored. API/list/detail may
derive presentation state `scheduled_wait` plus the canonical instant.

### W4-1: due-time, wakes, lanes, and clocks

All due decisions use an injected timezone-aware UTC wall clock. Sweep delays
use the injected monotonic clock and are bounded to at most five seconds; the
coordinator never sleeps directly until a far-future wall instant. It
reevaluates wall time after every bounded wake, so DST, timezone changes, and
forward/backward wall-clock jumps do not create an unbounded sleep or busy
loop. A run 365 days out remains dormant while normal immediate work is still
swept.

Both coordinator entry paths enforce due-time:

- `coordinator_candidates(now=...)` excludes a queued run whose derived
  `scheduled_at` is later than `now`.
- Pending-wake processing loads the run before submission. A real
  `run_admitted` wake for a not-due run is completed with outcome
  `scheduled_not_due` and does not submit or promote it. The indexed bounded
  sweep discovers it when due; correctness does not depend on retaining or
  repeatedly polling the original wake.

The store's compare-and-set lane promotion repeats the due check, closing the
race between selection and claim. Future scheduled runs follow this consumer
matrix:

| Consumer | Policy before due |
|---|---|
| coordinator candidates and pending wakes | excluded / completed deferred; never submitted |
| admission overlap, eligible queued predecessor, and lane ownership | ignored while future, so future work never rejects or blocks immediate work with the same concurrency key |
| queue position | absent from the immediate queue; project `scheduled_wait` instead |
| queued and nonterminal capacity quotas | counted, preserving bounded admission |
| running/worker counts | not counted until due promotion |
| desired-status/cancellation | cancellation allowed before due; projection and immutable evidence retained |
| foreground adoption/reconciliation | ineligible because scheduled admission is background-only |
| node retry `next_attempt_at` | unchanged and evaluated only after the run has fired |

Due runs enter the existing fairness order using their original admission
sequence; scheduling does not create an unbounded priority queue or allow a
future run to reserve a lane. Concurrency policy is evaluated atomically at
due promotion: `allow` may overlap subject to worker capacity, `queue` waits
for the lane, and `forbid` with an active same-key run terminates typed
`schedule_overlap_forbidden` rather than silently changing the policy.

### W4-2: fire-time authorization and snapshot staleness

Admission still performs the full normal trust, bundle, compatibility, input,
and package checks before sealing bytes. Scheduled admission additionally
persists the exact catalog source, package/definition/policy/input digests,
context-dependent risk digest, and—when applicable—showcase scenario and
bundle digests required for later comparison.

Immediately before due promotion, and before any node claim, the coordinator
performs a read-only revalidation:

- user workflow: resolve the same catalog source, recompute exact package and
  risk under the actual selected runner+runtime context, and require the
  current trust record to authorize those exact digests;
- verified showcase: force-reverify the bundled scenario and require exact
  scenario, bundle, package, risk, and capability-context parity; and
- all runs: require sealed definition/policy/input digests and execution
  identity to match the persisted admission record.

Deleted/replaced workflows, revoked trust, changed bundles, changed risk, an
incapable replacement runner or runtime, or corrupt/missing evidence produce
terminal typed `schedule_revalidation_failed`; no node is claimed and
execution never silently falls back. The sealed snapshot remains useful
evidence but does not override current authorization. Scheduled AI is allowed
because no consent contract exists, but it receives the same actual
runner+runtime capability recheck.

### W4-3: cancellation, showcase, and Desktop

Cancelling a not-due run uses the existing desired-status transition and
retains the run directory, journal, and audit projection; it does not delete
the immutable snapshot. A cancelled run can never become due or consume a
worker.

The scheduling showcase changes from `schedule_required` to supported once
`schedule_at` is present. Desktop Review & Run provides immediate **Run** and
one-shot **Run later** controls, submits the canonical request field, renders
Scheduled with the UTC/localized instant, supports cancel-before-fire, and
never claims that a cron job was created. The legacy CLI cron wrapper and its
schedule-kind confirmation are unchanged. Recurrence remains out of scope.

## Cross-cutting invariants

`agent_backed_features` is the single classification source for validator and
execution enforcement. Runner capabilities, runtime capabilities, and
entitlement are independent and thread consistently through catalog, detail,
admission, execution, and fire-time. Existing run classes receive no new
metadata, so their digests are unchanged. The verified cache stores no
context-dependent compatibility or risk. Legacy REST flat values stay
compatible. Scheduled identity is canonical in projection metadata and
derived everywhere else. Every refusal
before execution has zero side effects beyond the admitted scheduled run's
typed terminal audit record where applicable.

## Verification strategy

Mandatory named coverage includes: real worker MCP startup/tool-schema
delivery/PID reaping and cleanup on every early exit; failed-server and
`codex_app_server` zero-provider-call tests; prospective/actual runtime-mode
classifier parity; OTTO/LOOP24 HTTP tool-loop classification and their
structured-tool-call gateway contract; the API/coordinator production-binding
invariant; capable and incapable projections from one raw authenticated cache
entry; distinct risk digests accepted under their matching contexts; every
`RunExecutionLimits` field and the negative assertion that run-level
`max_iterations` does not exist; mixed-run concurrency; v3.0.2 REST and CLI
entitlement fixtures;
foreground adoption/rejection of the legacy CLI fixture; non-AI explicit-real
misclassification; every agent-runner consumer under deterministic
entitlement; legacy flat REST values unchanged; authenticated-boundary input
translation, declared-input errors, read-once fixtures, raw-data
non-projection, and manifest-digest idempotency; CLI
no-token-but-incompatible behavior; schema 13→14 and newer-version refusal;
projection-only namespace rebuild plus every other rebuild/integrity path;
real pending-wake deferral; lane/quota/queue-position matrix; bounded
wall-clock jump tests;
fire-time revocation/replacement/capability failures; cancellation retention;
and Desktop scheduling E2E.

Every row in the failure table maps to a named test in the release
verification document. No consent threat-model table exists because consent
is not part of the solution.

## Stop conditions

- Per-run claim limits require resizing or rebuilding shared scheduler pools.
- The selected runner cannot declare immutable capabilities, the effective
  runtime/tool-loop mode cannot be classified without credentials, network,
  or a subprocess, or catalog/admission/fire-time cannot consume the same
  server-owned context.
- A real-worker package-MCP contract cannot be proven without external
  network or billable inference.
- The worker cannot guarantee required-MCP startup before model traffic and
  shutdown/restoration across every early exit.
- Either generated brand gateway ceases to present the structured OpenAI
  tool-call contract required by Hermes' worker loop.
- Context-dependent risk cannot be removed from the authenticated cache.
- Legacy CLI showcase rows cannot be classified deterministic without
  mutating their metadata/start digest.
- Declared-input validation cannot coexist with the v3.0.2 flat-values REST
  contract.
- Any schema/rebuild/recovery path cannot derive and parity-check
  `scheduled_at` from projection metadata.
- Either pending-wake processing or lane promotion can bypass due-time or
  fire-time revalidation.
- Removing the CLI AI token makes the MCP-incapable CLI tour appear runnable.
- A full failure-table-to-test mapping cannot be produced before release.
