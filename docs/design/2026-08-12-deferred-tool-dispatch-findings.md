# Deferred Tool Dispatch Failure Findings

**Status:** Draft findings for discussion; no implementation authorized

**Date:** 2026-08-12

**Audience:** Engineers maintaining Hermes progressive tool disclosure and the
OTTO Gateway OpenAI-compatible adapter.

**Post-read action:** Reproduce the failure, distinguish it from a connector
or GitLab API failure, and evaluate the proposed remediation without relying on

## Executive summary

The LOOP24 Desktop test did not fail inside GitLab. The model emitted a
textual tool-call wrapper naming the deferred connector tool
`gitlab_list_group_projects` directly. That tool was not in the OpenAI
request's declared `tools[]`; Hermes had replaced plugin tool schemas with the
three progressive-disclosure bridge tools `tool_search`, `tool_describe`, and
`tool_call`.

OTTO Gateway 3.2.0 therefore followed its current safety contract: an
undeclared wrapper name with no safe schema overlap remained assistant text.
Hermes received the literal wrapper, found no structured tool call, and ended
the turn. The GitLab connector was never invoked.

The old and new Ericsson GitLab tools do not have different registration
paths. They are all registered by the same plugin loop with the same toolset,
availability check, handler factory, and policy surface. The behavioral
difference was the outer call generated by the model:

```text
Working:
  tool_call(name="gitlab_list_repository_tree", arguments={...})

Failed:
  gitlab_list_group_projects(group="...", recursive=true, ...)
```

The correct first-class fix is to make the progressive-disclosure contract
unambiguous after `tool_describe`. The recommended defense-in-depth fix also
teaches the gateway to route an undeclared textual wrapper through an
explicitly declared, schema-validated `tool_call` dispatcher. Hermes' existing
scoped deferred-tool gate remains the authority that decides whether the inner
name may execute.

## User-visible symptom

The user submitted a fresh-session prompt asking Hermes to use only the
Ericsson GitLab connector, recursively explore
`sd-macs-att-rnam-hosting`, and avoid terminal, curl, browser, and generic web
tools.

The only visible result was:

```json
{"tool_call":{"name":"gitlab_list_group_projects","arguments":{"group":"sd-macs-att-rnam-hosting","recursive":true,"max_groups":50,"max_projects":100}}}
```

The expected result was a structured tool invocation followed by a bounded
GitLab hierarchy result or a connector-generated error.

## Verified runtime evidence

### Installed versions

- The Windows installation updated the LOOP24 Hermes checkout from
  `2329336abc973a799e7775867d45f6f833252638` to
  `d789e287891e5aea7b9899330c759c1bc50681f3`.
- The Hermes checkout therefore contained the v5.5.3 GitLab descendant-order
  correction.
- The independently running OTTO Gateway reported version 3.2.0.
- Gateway 3.2.0 already contains full-turn streaming buffering for textual
  tool-call wrappers. The incident is not the pre-3.1.3 chunk-boundary bug.

### Failing turn timeline

The remote Windows agent log records one fresh Desktop turn:

1. At `21:14:09.513`, Hermes started session
   `20260812_211409_338c54` with no prior history.
2. At `21:14:15.287`, Hermes successfully executed `tool_describe` and
   returned 1,358 characters. This proves the first gateway wrapper was
   promoted to a structured call.
3. The raw gateway frames then show a second fenced wrapper naming
   `gitlab_list_group_projects` directly.
4. There is no `agent.tool_executor` entry for
   `gitlab_list_group_projects` during this turn.
5. At `21:14:19.431`, the turn ended after two API calls, one tool turn, and a
   175-character assistant response. That response length matches the leaked
   wrapper.
6. The later short session containing “GitLab group projects listing request”
   was auxiliary title generation, not a post-tool continuation.

### Control observation from the earlier turn

The earlier 20:20 test used the same new `gitlab_list_group_projects` tool but
produced the correct nested bridge call:

```json
{
  "tool_call": {
    "name": "tool_call",
    "arguments": {
      "name": "gitlab_list_group_projects",
      "arguments": {

        "max_projects": 100
```

Hermes then invoked the underlying connector twice and logged the connector's
`invalid_input` response. This control proves all of the following:

- the new tool was registered and reachable;
- the bridge could dispatch it;
- the gateway could surface the outer `tool_call` wrapper; and
- the 21:14 failure occurred before connector execution.

## Architecture involved

### Hermes progressive disclosure

Hermes classifies every non-core plugin or MCP tool as deferrable. When any
deferrable tools are available, the model-facing tool list keeps core tools
and replaces plugin/MCP schemas with three stable bridge schemas:

1. `tool_search` discovers deferred names;
2. `tool_describe` returns one deferred tool's full parameter schema; and
3. `tool_call` dispatches the selected name and argument object.

Describing a tool does not mutate the model-facing `tools[]` on the next API
call. That is intentional: dynamic schema mutation would weaken prompt-cache
stability and make each conversation turn's tool prefix variable.

The `tool_call` handler reconstructs the pre-assembly catalog, verifies that
the inner name belongs to the current session's enabled toolsets, validates
required arguments, and only then dispatches the underlying tool.

### OTTO Gateway wrapper coercion

The Kiro-backed gateway can receive a textual wrapper such as:

```json
{"tool_call":{"name":"get_weather","arguments":{"location":"Paris"}}}
```

For an OpenAI-compatible client, the gateway buffers tool-enabled streaming
text and attempts to convert that wrapper into native
`choices[].delta.tool_calls`. The extractor accepts:

- an exact name present in the request's declared tools; or
- an invented name whose argument keys safely match one declared tool schema.

If neither rule applies, the gateway preserves the text. This prevents an
undeclared or prompt-injected name from becoming executable merely because the
model printed JSON.

### Ericsson GitLab registration

Every Ericsson GitLab schema, including both the original repository tools
and the newer exploration tools, is registered by one loop. Each registration
uses:

- toolset `ericsson-gitlab`;
- the same configuration-backed availability check;
- the same handler factory;
- the same JSON success/error envelope; and
- the same plugin lifecycle.

The new `gitlab_list_group_projects` schema has a `group` argument instead of
the repository tools' `project` and `ref` arguments, but that schema difference
does not change registration or bridge eligibility.

## Confirmed causal chain

1. Hermes offered `tool_search`, `tool_describe`, and `tool_call`; the
   connector tool itself was deferred.
2. The model called the declared `tool_describe` bridge correctly.
3. The result returned the connector name, description, and parameter schema,
   but did not restate a machine-readable next-call envelope.
4. The model treated the described name as if it had become directly
   callable.
5. Gateway 3.2.0 found that `gitlab_list_group_projects` was absent from the
   declared `tools[]`.
6. Its argument keys (`group`, `recursive`, `max_groups`, `max_projects`) did
   not safely match an offered schema, including the outer `tool_call` schema
   (`name`, `arguments`).
7. The gateway failed open to text, as designed.
8. Hermes received assistant text with `finish_reason=stop`, so no tool
   execution branch ran.

## Root cause

The progressive-disclosure bridge has an integration gap between description
and dispatch:

- Hermes relies on the model to remember that a described deferred tool must
  still be invoked through `tool_call`.
- The `tool_describe` result exposes the hidden tool's schema but does not
  return an explicit, machine-readable dispatch contract.
- The gateway safely understands declared tools and schema-based aliases, but
  it does not understand that a declared `tool_call` function is a dispatcher
  for deferred inner names.

This gap is model-dependent and therefore intermittent. Adding more GitLab
tools did not create a different registration class; it increased the catalog
surface and supplied a new natural-language path that exposed the pre-existing
assumption.

| Streaming chunks split the fence incorrectly | Ruled out | 3.2.0 buffers the full tool-enabled turn; the first wrapper also succeeded |

| The v5.5.3 GitLab ordering correction failed | Not yet tested | The connector never ran in the new turn |

| Wake-word or microphone errors affected the turn | Ruled out | Those failures are on an unrelated audio path |

## Remediation options

### Option A: Strengthen only the Hermes description contract

Return a machine-readable `invoke_via` contract and an explicit next-step
instruction from `tool_describe`. Also strengthen the stable bridge schema
description to say that describing a tool never makes it directly callable.

**Advantages:** Corrects the contract at its owner, has a very small footprint,
and preserves gateway safety behavior.

**Limitation:** It remains an instruction-following solution. A model can
still ignore the instruction and emit the hidden name directly.

### Option B: Add only dispatcher-aware gateway recovery

When a wrapper names an undeclared tool and the request explicitly offers a
schema-validated `tool_call` dispatcher, convert the call into:

```json
{
  "name": "tool_call",
  "arguments": {
    "name": "original_hidden_name",
    "arguments": {"original": "arguments"}
  }
}
```

**Advantages:** Deterministic recovery across models and clients using the
same dispatcher contract.

**Limitation:** The gateway gains knowledge of a dispatcher convention. The
recognition must be exact and must not weaken the existing undeclared-tool
fail-safe when no valid dispatcher is offered.

### Option C: Contract plus narrowly gated recovery — recommended

Implement Option A as the primary contract and Option B as defense in depth.
The gateway may only route through a declared function named `tool_call` whose
schema requires string `name` and object `arguments`. The inner tool still
passes through Hermes' scoped catalog and required-argument checks.

This does not grant new authority. It produces the same structured call the
model was already allowed to make directly against the declared dispatcher.

### Option D: Dynamically add described schemas to `tools[]` — rejected

After `tool_describe`, add the selected connector schema to the next API call.
This resembles native tool calling but mutates the model-visible tool prefix
mid-conversation, undermines prompt caching, and creates more complicated
history/replay semantics. It conflicts with the purpose of progressive
disclosure.

## Safety and compatibility constraints

Any accepted correction must preserve these invariants:

1. An arbitrary textual wrapper cannot execute unless its outer tool is
   declared or it is routed through an explicitly declared dispatcher.
2. The gateway must retain current fail-open-to-text behavior when no valid
   dispatcher exists.
3. Hermes remains the authority for whether an inner deferred name belongs to
   the current session's toolset scope.
4. `tool_call` cannot recursively invoke bridge tools or core tools.
5. Describing a tool must not mutate the conversation's model-facing tool
   list or cached prefix.
6. Native structured tool calls and directly declared tool names retain their
   current wire shape.
7. OpenAI streaming, OpenAI non-streaming, Anthropic, and Ollama adapters must
   preserve their existing protocol-specific output shapes.
8. The fix must be generic to deferred dispatch; it must not special-case
   Ericsson or GitLab names.

## Acceptance criteria

The remediation is acceptable when:

1. `tool_describe` tells the model, in machine-readable and human-readable
   form, to invoke the result through `tool_call`.
2. The exact 21:14 fenced wrapper is converted to a native call of
   `tool_call` when that dispatcher is declared.
3. The resulting nested arguments retain the original connector name and
   argument object byte-for-meaning.
4. The same unknown wrapper remains plain text when no valid dispatcher is
   declared.
5. A lookalike or malformed dispatcher schema does not enable recovery.
6. Hermes accepts an in-scope deferred name and rejects an out-of-scope,
   bridge, or core name after recovery.
7. The installed Windows UAT log contains, in order, `tool_describe`,
   `tool_call`, and `gitlab_list_group_projects` execution evidence.
8. The GitLab hierarchy request then either succeeds or returns a connector
   error, proving the request reached the connector and separately exercising
   the v5.5.3 ordering correction.
